## 已修正項目

### 印堂編號：`EX-HN3` → `GV24+`

`app/HealthPages.tsx` 原本用 WHO 國際碼 `EX-HN3`，但本數據集嘅國標正碼係 **`GV24+`**。上游 `lib/atlas.ts` 已註明：

> GB/T 12346-2021 inserts Yintang between GV24 and GV25 without renumbering the existing points.
> `aliases: 'EX-HN3；GV29（舊編號）；印堂'` —「本應用按現行國標使用 GV24+，舊編號僅用於檢索。」

原本嘅寫法唔算壞連結（App 會經 alias 檢索到），但：
1. 卡片顯示嘅穴碼會同 3D 面板側欄（顯示 `GV24+`）**唔一致**；
2. 用咗明文標示為「僅供檢索」嘅舊碼。

已改為 `GV24+`，並把描述由「經外奇穴」更正為「原屬經外奇穴，現行國標歸入督脈」。

### 順帶記錄：URL `+` 陷阱

`GV24+` 嘅 `+` 在 query string 會被解碼成**空格**。所以 `/?points=GV24+`（手打、未編碼）會靜默變成 `GV24`＝**神庭**，即係另一個穴。必須用 `%2B`：

| 網址 | 結果 |
| --- | --- |
| `/?points=GV24%2B` | ✅ 印堂 |
| `/?points=GV24+` | ❌ 神庭（靜默錯誤） |

本應用所有內部連結都用 `encodeURIComponent()`（`app/HealthPages.tsx`、`app/AtlasApp.tsx`、`app/Combinations.tsx`、`app/Pronunciation.tsx`），所以**程式產生嘅連結無問題**；只有手寫網址要小心。`GV24+` 係全數據集唯一含 `+` 嘅編號。

## 審查期間發現並修復：測試套件全紅

跑項目自帶測試時發現 **49 項失敗**（156 項中）。追查後確認同穴位幾何無關，而係本版**繁體化未完成**所致，共兩處漏網：

| 漏網位置 | 原因 | 影響 |
| --- | --- | --- |
| `scripts/test.mjs` | 首輪轉換只掃 `app/ components/ lib/ public/`，`scripts/` 從未被掃過 | 測試斷言仍期望簡體字串，415 個字元不符 |
| `lib/mesh-registration.json` | 中文以 **`\uXXXX` 轉義**儲存（6399 處、0 個字面中文字元），純文字轉換完全睇唔到 | 116 個 `proportionNote` 及大量 `note` 仍是簡體（即 `/learn`、`/care` 等頁面顯示得唔一致） |

處理：

1. `scripts/test.mjs` 用 OpenCC `s2hk` 轉換（保護 URL）→ 138 通過
2. `lib/mesh-registration.json` 以 **JSON-aware** 方式轉換（解析後轉字串值，再以原本 `ensure_ascii=True, separators=(',',':')` 風格重新序列化，byte 長度不變）→ 157 個字串轉換
3. 繁體化改動了檔案 bytes，但被記錄的 SHA-256 仍是舊值 → 重釘：
   - `lib/mesh-registration.json`：`vesselRoutes.specSha256`（`232f200d…` → `d3ba3afd…`）、`lowerLeg.specSha256`（`4cf959d6…` → `e8a68156…`）
   - 19 個 `lib/*-course.json` 的 `registrationSha256`（`614c7797…` → 新 registration hash）

**結果：156 / 156 全數通過。**

> ⚠️ 誠實邊界：重釘之後，完整性測試證明嘅係「資料與記錄一致」，**唔再**等同「與上游位元組相同」——繁體化本身就係本版改動。
>
> 另外，上游 `scripts/` 內嘅 Python 工具（85 個檔）**刻意未轉換**，一來佢哋唔屬網站內容，二來佢哋嘅 `scriptSha256` 記錄仍指向「未經修改的上游腳本」，保留咗一層有用嘅出處證明。副作用：若重跑該等腳本，寫入嘅註記會還原成簡體（幾何結果不受影響）。
